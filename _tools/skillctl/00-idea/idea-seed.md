# idea 种子 · skillctl(N=1 完整闭环的题面)

> 这是 Path A 的原始输入(requirement notes / 未结构化)。写于 2026-07-03。
> 目的:开一个真内部小工具,单兵全程 idea→设计→编码→测试→ship,全程走 skill 链,
> 攻北极星头号缺口(至今 0 次干净 idea→prod 完整闭环)。工具本身必须解决我真实的痛。

## 我是谁在用
- 我(skill 平台 builder,单兵)。天天维护一套 157 个 SDLC skill 的 library。
- 每次强化/折入一个 skill(改 SKILL.md / references / CHANGELOG),都要重新打包成 zip、
  核对没丢文件、CHANGELOG 有没有 bump 版本、库总数还是不是 157。

## 真实的痛(全部亲历,非假设)
1. **本机没有 `zip` 命令**。每次折 skill 都手写 Python zipfile 从解压树重打包。易错。
2. **打包易丢/多文件**。D-055 折方向1 时,`unzip -l` 报 24 条目、实际应 19(差的是目录条目),
   靠人肉逐条核对才没丢文件。没有自动的"条目数守恒"校验。
3. **CHANGELOG 是否 bump 全靠记**。改了 SKILL.md 却忘记加 CHANGELOG 版本条目 → 无人拦。
4. **库恒 157 这个不变量靠肉眼**。多打/漏打一个 zip 没人报警。
5. **总表 `docs/技能库总表.csv` 有 154 行,但库是 157**。这个 3 条的缺口一直没对齐,
   没有工具能把"磁盘上的 zip 集合"和"总表登记"和"叙述里说的 157"三方对账。
6. **19/157 真强化覆盖率没有机器可读的记录**。散在 CLAUDE.md / DECISIONS.md 的叙述里,
   每次要回答"哪些 skill 真被强化过/覆盖率多少"都得翻记忆,数字还会漂(早期写 155)。

## 我想要的东西(粗略,未结构化)
一个本机 CLI,叫 `skillctl`,至少能:
- **pack**:把一个 skill 的解压目录重新打成规范 zip,自动做条目守恒校验 + testzip,不用我手写 Python。
- **lint**:检查一个 skill 包/目录是否合规——SKILL.md frontmatter 齐不齐、CHANGELOG 有没有对应版本条目、
  改动了内容有没有 bump 版本。
- **count**:扫 `完稿/N*/*.zip`,报库总数,和"恒 157"这个期望值对账;顺带和总表 CSV 行数对账,
  把 157 vs 154 这类缺口直接列出来。
- **coverage**:一个覆盖度仪表盘——把 157 个 skill 列出来,标每个的 macro 路径归属、当前版本、
  是否"真强化过"(数据源待定,可能要我维护一个小清单),给出 19/157 这类覆盖率。

## 约束/边界(我知道的)
- 纯本机、单人用,不上线、不给别人、无网络。Python 3(本机有 3.12 和 conda 3.13)。
- 只读 `完稿/N*/*.zip` 和 `docs/*.csv`;写只落在自己工作区(不碰别人仓,红线)。
- 不追求花哨,追求"每次折 skill 我真的会用它、它真的拦下过错"。
- 有界:4-6 周单兵能从零 ship 到天天用。

## 成功长什么样
- 下次折 skill 时,我用 `skillctl pack` 打包、`skillctl lint` 过门、`skillctl count` 确认恒 157,
  而不是手写 Python + 肉眼核对。
- 至少拦下一次真错(丢文件 / 忘 bump CHANGELOG / 库数漂了)。
- 全程用 skill 链产出的工件(PRD / 技术方案 / 任务分解 / PR)本身,成为"skill 链能不能扛真 idea→prod"的证据。
